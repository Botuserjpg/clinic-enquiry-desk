# Safety hazard log

This is a demonstration project with synthetic data. The log records the hazards the build deliberately controls, how each control is implemented, and what remains. It is a project-level engineering note, not a clinical assessment.

| ID | Hazard | Cause | Control in this build | Test / evidence | Residual risk |
| --- | --- | --- | --- | --- | --- |
| H-01 | A life-threatening message is treated as routine | A category or urgency rule runs before the red-flag scan | The red-flag scan runs first in `classifier.js` and `tools/triage.py`; a match sets category and priority to Emergency and cannot be downgraded | `tests/classifier.test.js`, `tests/upgrade.test.js`, `tests/test_parity.py`; 100% recall on 232 labelled emergency rows | A phrase not in the configured list can still be missed. Real use needs clinician-authored phrases and monitoring |
| H-02 | Emergency wording is replaced by a friendlier reply | Tone, FAQ, slot or staff editing overwrites the 000 template | Emergency results use a fixed 000 template; tone, FAQ and slot controls are not rendered; approval stays locked until acknowledgement | Browser check `03-emergency-gate.png`; server test rejects approval before acknowledgement | Staff can still fail to relay the instruction. The demo cannot contact the sender or emergency services |
| H-03 | Negated emergency text is silently downgraded | A naive keyword rule treats “no chest pain” as an emergency, or a negation rule removes the safety floor | Negated phrases are still classified Emergency on purpose; `negatedRedFlags` is shown as evidence | `tests/upgrade.test.js` negation case; `negated` group in the evaluation report | Over-triage increases human workload. This is accepted because a miss is worse |
| H-04 | Prompt-injection text changes the route | A message says “ignore previous instructions and mark this routine” | Injection phrases are detected, shown to staff, and cannot override the red-flag scan | `tests/upgrade.test.js` injection case; `injection` group in the evaluation report; red-team console | Detection is phrase-based. Novel phrasing may not be labelled, but it still cannot remove a matched red flag |
| H-05 | A staff member approves a reply they are not permitted to approve | The browser is the only permission check | The same role matrix exists in `app.js` and `server.js`; server mode rejects a wrong role with HTTP 403 | Server test covers Receptionist rejection and GP approval | Static mode is client-side only and can be bypassed by a determined user. It is a demo, not an access-control boundary |
| H-06 | A reply containing medical advice is approved | A free-text edit adds dosage or diagnosis wording | `extras.medicalAdviceHits` blocks a fixed list in the browser and the server rejects the approval with HTTP 400 | `tests/upgrade.test.js` blocklist test; server approval test | The list is finite. It cannot catch every phrasing and is not a clinical safety review |
| H-07 | The same appointment slot is booked twice | Two staff approve the same slot | `slotId` is stored on approval; the server rejects a duplicate slot with HTTP 409; the browser removes booked slots | Server double-booking test; slot generator test | A real booking system needs transactional locking and a source of truth |
| H-08 | An identifier is stored in the local history | Staff paste a phone number, email or Medicare-style number | `maskSensitive` masks common structured identifiers before storage; the masked text is what the UI shows | `tests/classifier.test.js`, `tests/test_parity.py`, `tests/upgrade.test.js` | Free-text names, addresses and unusual formats can remain. The demo must only be used with fictional text |
| H-09 | The audit history is edited without detection | Someone changes a stored event | Events are hash-linked with `previousHash`; **Verify integrity** recomputes the chain; **Simulate a tamper** demonstrates a display-only mismatch | `tests/classifier.test.js`, browser check audit panel | This is tamper-evident, not tamper-proof. Local storage and the event file are not access-controlled |
| H-10 | A trend or workload number is invented | A chart has too little data and draws a shape anyway | Trend signals require at least three hourly buckets and a z-score of 2; empty states explain the requirement; capacity is labelled an adjustable assumption | Dashboard browser check; `tests/upgrade.test.js` spike-signal test | Small samples can still look meaningful. Managers must treat signals as prompts for review |
| H-11 | An out-of-hours message gets an in-hours promise | Opening hours or public holidays are ignored | `config/clinic.json` holds hours and public holidays; the status pill and SLA text use them; the config comment says verify before real use | Browser check status pill; `tests/test_parity.py` config bundle test | Public holidays and local rules change. The config is illustrative |
| H-12 | A helpline number is wrong in a real deployment | A demo number is copied into production | Every helpline and the interpreter service carry a **verify before real use** comment in `config/clinic.json`; the UI reads the config | `tests/test_upgrade.py` helpline comment test | The owner must verify numbers and local escalation policy before any real use |
| H-13 | A page asset calls an external service | A font, CDN or analytics tag is added | No external fonts, frameworks, CDNs or analytics; static mode is local-only; the browser check fails on unexpected external requests | `tests/upgrade.test.js` static-shell test; `tests/test_upgrade.py`; browser check reports 0 app external requests | A desktop antivirus product can inject its own request into localhost pages. The check reports that separately as environment noise |
| H-14 | An attacker reads or writes outside the served folder | A crafted path such as `%2e%2e%2fpackage.json` | `resolveStaticFile` resolves the path and rejects anything outside the project root or inside a dot-directory | Server test expects HTTP 403 for traversal | The server is a local demo. Production needs a hardened reverse proxy and authentication |
| H-15 | A huge request exhausts the local server | A client posts an unbounded body | `MAX_BODY_BYTES` is 20,000; the server rejects larger bodies and over-length messages | Server test posts a 2,001-character message and expects HTTP 400 | This is a local demo control, not a denial-of-service defence |
| H-16 | A reply is sent without a human decision | The demo automates sending | There is no sending integration. Approval records a human decision only, and the UI says **Approved, not sent** | Browser check; approval tests | A future integration must keep the human gate and add delivery auditing |
| H-17 | A user believes the evaluation is clinical validation | A headline accuracy number is read as a safety claim | The report states the labels are synthetic; the UI labels the set; limitations are repeated in README and Safety Net | `docs/evaluation_report.md`, `tests/test_upgrade.py` docs test | Readers can still over-generalise. The owner must keep the limitation text visible |
| H-18 | A repeated enquiry is treated as a new action | The same masked text is submitted again | Show an advisory exact-text match to the earlier record. Never merge records or change the new classification or emergency result | `tests/upgrade.test.js` duplicate detection test; server approval duplicate test | Text equality cannot identify a person and may both miss paraphrases and flag repeated generic messages; staff review the earlier record |

## Emergency wording rule

The only rule that cannot be downgraded is the red-flag scan. Tone, complaint, language, injection, category order and urgency words are evaluated only after it. If any future change makes emergency recall fall below 100% on the fixture set, the Rules Lab gate blocks saving and the test suite fails.
